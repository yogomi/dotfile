# ⚠️ 絶対禁止事項（最優先・全セッション共通）

- **git commit は「コミットして」と明示的に指示された場合のみ行う。**
- **git push は「pushして」と明示的に指示された場合のみ行う。**
- 作業の区切り・変更の蓄積・会話の流れに関わらず、commit / push を自発的に提案しない。
- 「コミットしましょうか？」「pushしますか？」などの提案も禁止。

# プロファイル情報

## 基本方針

- 文章はやや硬めの文体で回答してほしい。
- 回答の末尾に「何かしましょうか？」などの提案を毎回つけないでほしい（本当に有益な場合のみ）。
- 「資料を書いて」「メモしておいて」「記録しておいて」など、形式の指定がない場合はMarkdownで出力する。
- Markdownを使う場合はGitHub Flavored Markdownに従う。

## git 操作

- git commit は明示的に依頼された場合のみ行う。作業の区切りでも自動的にコミットしない。
- git push は提案しない。push が必要かどうかはユーザーが判断する。
- 未コミットの変更が残っていると判断した場合、以下の振る舞いを続ける：
  - 毎ターンの応答末尾にコミットのリマインドを追記する
  - 質問への回答や説明は行うが、新たなファイル変更には着手しない
  - ユーザーがコミットを完了した、または「コミット不要」「スキップして」など
    コミットしない意思を明示した場合のみ、通常の作業に戻る
- コミット完了後、必要と感じた場合はリマインド前の作業への誘導を行う
- コミット前にlint・型チェックのスクリプトやコマンドが存在する場合は必ず実行し、
  エラーがないことを確認してからコミットする
- `git add -A` や `git add .` は絶対に使わない。
  `.DS_Store` や `.env` などの不要ファイル・機密ファイルを誤ってコミットする原因になる。
  必ずファイル名を明示して `git add <file>` でステージングすること。

## 作業開始前の確認フロー

ファイルの作成・編集・削除を伴う作業を始める前に、以下の手順を踏むこと：

1. 変更の目的・対象ファイル・変更内容の概要を説明し、必要であれば議論する
2. 合意が得られたら「この内容で作業を進めてよいですか？」と一度だけ確認する
3. 承認を得てから作業を開始し、個々のファイル操作ごとに再確認はしない

ただし、ユーザーが「すぐやって」「確認不要」と明示した場合はこの手順を省略してよい。

## コード共通ルール

- コードは一行に100文字まで。
- 行末のスペースやタブは禁止
- 改行コードはLF
- GitHubでpull requestを作成するときは日本語で書いて。
- pullリクエスト作成などでコードを変える際には、変える前と同等レベルのコメントを残すこと。

## ルールファイル

作業開始前に対象ファイルを Read ツールで読み込むこと。

- Web開発（React/Express/MUI等）→ `~/.claude/rules/web.md`
- Python → `~/.claude/rules/python.md`
- 映像・動画処理（ffmpeg/NVENC等）→ `~/.claude/rules/video.md`
- 翻訳プロジェクト（Whisper/NLLB等）→ `~/.claude/rules/translation.md`

## セカンドオピニオン

以下の場面では、メインセッションとは別の新規コンテキストでセカンドオピニオンを取得し、
参考意見として提示する：

- アーキテクチャや技術選定など、後から変更しにくい設計判断を提示するとき
- 100行を超える diff をレビューするとき

取得方法と制約：

- general-purpose サブエージェントを、メインセッションと異なるモデル（Opus 等）を
  指定して起動し、会話の経緯を含めず判断材料だけを渡してレビューさせる
- 外部AIサービス（Gemini / Antigravity 等）にはコードを渡さない
- セカンドオピニオンは判断材料の一つとして扱い、最終判断は Claude とユーザーで行う

## コンテキスト管理

話題が切り替わった、または会話が長くなってきたと感じたら、以下を提案する：

1. それまでの要点・決定事項・未解決事項を Markdown ファイルに書き出す
2. その上で /clear（話題転換時）または /compact（同一話題の継続時）の実行を促す

提案は区切りの良いタイミングで行い、作業の途中では割り込まない。

## サブエージェント運用

詳細は `~/.claude/docs/agent-operations.md` を参照。

- 仕様が確定した実装・テスト作成・機械的な修正は implementer サブエージェント（Sonnet）に
  委譲する
- コードベースの横断調査は Explore サブエージェントに委譲し、結論だけを受け取る
- 複雑なデバッグの原因調査はサブエージェントに委譲し、仮説と根拠だけを受け取る
  （モデルは調査の難度に応じて都度指定する）
- 設計判断はサブエージェントに委譲しない。メインセッションでユーザーと対話して決める
- 数行の修正や方針を対話で詰める作業はメインセッションで直接行う
